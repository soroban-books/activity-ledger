# Verified findings (spikes run against mainnet)

Every fact the design depends on, with how it was checked. Dates are 2026-10-24/25. Scripts are in `scripts/`. Re-run them when a fact matters; the network changes.

| # | Finding | How verified | Consequence |
|---|---|---|---|
| **F-1** | **Horizon v30 transaction records carry no `result_meta_xdr`.** Fields returned: `envelope_xdr`, `result_xdr`, `fee_meta_xdr`, `memo`, `fee_charged`, … | `curl https://horizon.stellar.org/accounts/{G}/transactions?limit=2` and listing the record keys; `scripts/spike3-horizon-meta.mjs` failed with `expected a string … got undefined` | Events cannot come from Horizon. Need the lake (F-3). |
| **F-2** | Horizon's earliest ledger is **58,812,481** (≈ 2025-09-07); latest was 65,119,758. | `GET https://horizon.stellar.org/` → `history_elder_ledger`, `history_latest_ledger`; first synced transaction for a test account dated 2025-09-07 | Discovery cannot see older activity (limitation 1). |
| **F-3** | Galexie public lake: one zstd `LedgerCloseMetaBatch` per ledger, 64,000 ledgers per partition. Config `{"ledgersPerBatch":1,"batchesPerPartition":64000,"compression":"zstd"}`. File ≈ 120–170 KB compressed, ≈ 1.1 MB raw. | `GET …/v1.1/stellar/ledgers/pubnet/.config.json`; fetched ledger 65,102,936 (HTTP 200, 170,361 B → 1,094,700 B) | Path formula in `src/sources/lake.ts`. Free, no credentials. |
| **F-4** | In transaction meta v4, contract events are in `operations[].events` (plain `ContractEvent`) and transaction-level `events` as `{stage, event}` wrappers (fee events). XDR enums decode to objects (`{name, value}`) in stellar-sdk 17.3.0, and unions to `{type, <arm>}` objects. | `scripts/spike4b.mjs`, `scripts/spike6.mjs`, `scripts/spike7.mjs`; a first decode attempt failed on `e.body.v0` until the wrapper was handled | `decodeLedgerMeta` handles wrappers and `enumName`. Learned the hard way: do not compare enums to strings. |
| **F-5** | **Classic payments also emit CAP-67 `transfer` events** in the lake meta: a 100-payment transaction produced 101 events (100 transfers + a fee event); data is `{amount, to_muxed_id}` when a memo id is present. Event topics for SACs carry the classic asset as 4th topic (`"USDC:G…"`, `"native"`). | Ledger 65,119,411 via `scripts/spike5-blend-tx.mjs`; also seen back at 2025-09-07 | One uniform event stream for classic + Soroban; no operation-based fallback needed for the covered window. |
| **F-6** | **Decoding one ledger's XDR with the SDK takes 4.3–8.2 s** (zstd itself 43–124 ms), 201–240 txs per ledger sampled, 4 cores. A sync of 100 transactions took ~7 min single-threaded; the main bottleneck is CPU. Network to Horizon also timed out intermittently (`ConnectTimeoutError`). | `scripts/profile.ts`; timings of `syncAccount` runs | Worker-thread pool built (3 workers on this machine). Native decoder is the T3 fix. First sync of a busy account will take a long time today. |
| **F-7** | Soroban RPC retention: `ledgerRetentionWindow` 120,960 ledgers (≈ 7 days); `oldestLedger` 64,998,797 when latest was 65,119,756. | `getHealth` against `mainnet.sorobanrpc.com` | RPC cannot serve tax-year history. |
| **F-8** | SDEX hourly prices work: XLM/USDC close = $0.178784 and BLND/USDC = $0.006027 at 2026-10-19T07:00Z; a real Soroswap swap in that hour implied $0.005977/BLND (0.8% apart). Horizon returns ratios as `close_r: {n, d}` (lower-case keys). | `scripts/check-prices.ts` | Pricing provider built; a first version failed because the keys are lower-case. |
| **F-9** | **Horizon lists transactions where the account is only the recipient of a Soroban router swap.** Tested 5 transactions, one recipient account (`GB3JCHJU…`), five different source accounts: all 5 listed, but only after paging past the first 200 results. **My first run reported 0/5 listed — wrong:** the list was newest-first and 200 deep, so older swaps were beyond page 1. | `scripts/test-r1.mjs` (flawed), `scripts/test-r1b.mjs` (paged until the list passed the target ledger) | Sync pages ascending from the start so depth is not an issue. Sample is narrow: one account, one protocol. |
| **F-10** | The lake also has per-ledger Parquet (`v1.1/stellar/parquet/pubnet/v1/date=YYYY-MM-DD/<ledger>.parquet`, ≈ 400 KB) with nested `transactions → operations → events {contract_id, topics, data}` (ScVals as bytes). Reading one with `hyparquet` needed an injected ZSTD codec and took ≈ 4.3 s. | `scripts/parquet-peek.mjs` | No faster than XDR decode in JS; not adopted. Revisit with a native reader. |
| **F-11** | Blend v2 pool events on mainnet match `pool/src/events.rs`: `supply/supply_collateral/withdraw/withdraw_collateral` → topics `[name, asset_contract, from]`, data `[tokens, b_tokens]`. Many `from` addresses are contracts (vaults), not user G accounts; real user accounts mostly emit the `*_collateral` variants. | RPC `getEvents` on FixedV2/YieldBloxV2 pools: `scripts/spike1-blend-events.mjs`, `spike2-find-users.mjs`, `find-blend-roundtrip.mjs` | Decoder keyed on these shapes; fixture `blend-roundtrip`. |
| **F-12** | Soroswap router emits `["SoroswapRouter","swap"]` with `{amounts[], path[], to}`; the pair emits `["SoroswapPair","swap"]` with `{amount_0_in, amount_0_out, amount_1_in, amount_1_out, to}` and `sync`. Asset transfers appear as separate CAP-67 transfers between user and pair. | `scripts/spike8-soroswap.mjs`; tx `32a3ec76…` | Router decoder exact when `to` is the account; generic heuristic reproduces the same trade (test). |
| **F-13** | A successful transaction's fee appears as two events: a positive charge then a negative refund, both `["fee", payer]` on the native SAC (e.g. 43,869 and −10,522 stroops → net 33,347). | tx `32a3ec76…` | `netFee` sums them. |

## What I got wrong along the way (kept for honesty)

1. **F-9 first result** (0 of 5 listed) was a pagination artifact; the corrected result is 5 of 5.
2. **Tideline-style assumption that Horizon meta exists** (F-1) failed on first contact.
3. The first `lake.ts` mapped contract events to `system` because enums are objects, not strings (F-4). Tests did not exist yet; the end-to-end spike caught it.
4. Before tests existed, an uninvolved account was assigned an `unclassified` event for a contract call it never made. The new test `an account not involved in a transaction gets no events` caught it; fixed by restricting to source/fee-paying accounts.
5. Zero-amount transfers produced empty events in the first real export; now skipped and tested.
