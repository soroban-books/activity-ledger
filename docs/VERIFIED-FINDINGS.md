# Verified findings (spikes run against mainnet)

Every fact the design depends on, with how it was checked. Dates are 2026-10-24/25. Scripts are in `scripts/`. Re-run them when a fact matters; the network changes.

| # | Finding | How verified | Consequence |
|---|---|---|---|

Need the lake (F-3). |
| **F-2** | Horizon's earliest ledger is **58,812,481** (≈ 2025-09-07); latest was 65,119,758. | `GET https://horizon.stellar.org/` → `history_elder_ledger`, `history_latest_ledger`; first synced transaction for a test account dated 2025-09-07 | Discovery cannot see older activity (limitation 1). **Update 2026-11-04:** the window slides. `history_elder_ledger` was 59,001,121 (2025-09-19T14:29:45Z), so it advances about one day per day. | **F-13** | A successful transaction's fee appears as two events: a positive charge then a negative refund, both `["fee", payer]` on the native SAC (e.g. 43,869 and −10,522 stroops → net 33,347). | tx `32a3ec76…` | `netFee` sums them. |
| **F-14** | **Sync time is network-bound, not decode-bound.** Warm decode of a full ledger is 0.3-1.2 s (zstd 9-55 ms, `fromXDR` 0.26-1.15 s, event conversion about 0.1 s). A lake file (170-280 KB) takes 4-37 s to download on the test machine (about 1 s round trip, about 25 KB/s per connection, about 120-170 KB/s in aggregate; IPv6 does not work there). Horizon's first response took 6-17 s (6.8 s to first byte; gzip shrinks 200 txs from 945 KB to 118 KB but time barely moves). A cold worker needs about 5 s to load the SDK. Per distinct ledger the floor is about 1.3-1.5 s on that link. | `scripts/profile.ts`, `scripts/bench-stages.ts`, `scripts/bench-timeline.ts` (per-request timeline), `scripts/bench-sync.ts` | F-6's 4-8 s per ledger was wrong or measured under cold/contended CPU. A native decoder (M7) would not help here. Real levers: fewer bytes (cache, shared cache, Soroban RPC for the last 7 days), earlier first results, reliability. Node's `fetch` has a fixed 10 s connect timeout that fails on slow links, so `src/sources/net.ts` is used instead. |

## What I got wrong along the way (kept for honesty)

1. **F-9 first result** (0 of 5 listed) was a pagination artifact; the corrected result is 5 of 5.
2. **Tideline-style assumption that Horizon meta exists** (F-1) failed on first contact.
3. The first `lake.ts` mapped contract events to `system` because enums are objects, not strings (F-4). Tests did not exist yet; the end-to-end spike caught it.
4. Before tests existed, an uninvolved account was assigned an `unclassified` event for a contract call it never made. The new test `an account not involved in a transaction gets no events` caught it; fixed by restricting to source/fee-paying accounts.
5. Zero-amount transfers produced empty events in the first real export; now skipped and tested.
6. **F-6 blamed XDR decode.** Profiling the whole pipeline (F-14) showed downloads dominate; decode is about 20% of one ledger's time.
7. **`horizon.ts` retry loop did not catch thrown network errors**, so one transient `fetch failed` aborted a whole sync. Fixed. `invokedFunctions` also decoded to NUL bytes (SDK returns a string wrapper, not bytes); fixed with a regression test on a real envelope.
